# 가입 전환 측정 계약

이 문서는 가입 안내 화면부터 로그인 시도, 계정·프로필 생성까지의 측정 기준과 보고서 실행 방법을 정리한다. 익명 행동과 실제 계정 생성은 서로 다른 모집단이며, 두 집단의 수치를 이어 붙여 하나의 전환율로 계산하지 않는다.

## 수집 이벤트

브라우저에서 기록하는 이벤트는 `signup_guide_view`, `signup_guide_cta`, `login_started`, `login_result` 네 가지다. 네 이벤트는 항상 익명 세션 해시로 소유자를 표시하며 계정 ID와 셀럽·LIVE·미션·혜택 ID를 담지 않는다.

- 안내 이벤트의 출처는 `signup.guide`다. `signup_guide_view`는 화면을 본 시점의 `guest`, `member`, `unknown` 상태를 기록한다. 나중에 로그인 상태가 확인돼도 과거 이벤트를 바꾸지 않는다.
- 로그인 이벤트의 출처는 `signup.login`이다. 한 로그인 시도는 UUID v4 nonce 하나를 쓰고, 시작·실패·성공 관찰을 같은 nonce로 묶는다. 실패 뒤 같은 시도가 성공하면 두 관찰을 모두 보존한다. 사용자가 다시 시도하면 새 nonce를 발급한다.
- 공통 속성은 `channel`, `landing`, `guide`, `browser`, `os`, `locale`이며 값은 고정된 분류만 허용한다. 이벤트별 속성도 고정돼 있어 누락·추가 속성, 잘못된 자료형과 임의 문자열을 RPC에서 거부한다.

서버에서 기록하는 `account_created`, `profile_completed`는 각각 `app_users`와 `user_profiles` INSERT가 성공한 트랜잭션에서 생성한다. 출처는 `server.commit_projection`, 속성은 빈 객체, 소유자는 원본 행의 계정 ID다. 이벤트 시각과 결정적 멱등성 키도 원본 행에서 정한다. 원본 행이 없거나 시각·키가 맞지 않으면 직접 만든 서버 이벤트를 거부한다.

프로젝션은 측정 실패 때문에 가입 처리를 취소하지 않도록 오류를 경고로 남기고 원본 INSERT를 계속한다. 같은 트랜잭션이 롤백되면 생성된 이벤트도 함께 사라진다. 마이그레이션 이전 데이터는 소급 생성하지 않는다. 따라서 운영 수치는 원본 테이블을 기준으로 보고, 이벤트 커버리지는 별도로 확인한다.

## 보고서 실행

보고서는 `psql`에서 시작 시각과 종료 시각을 반드시 전달해 실행한다.

```bash
psql "$DATABASE_URL" \
  -v from='2026-09-01T00:00:00+09:00' \
  -v to='2026-09-08T00:00:00+09:00' \
  -f scripts/report-signup-conversion-funnel.sql
```

시간 구간은 `[from,to)`다. `from`은 `to`보다 앞서야 하고, `to`는 실행 시점 이후일 수 없으며, 조회 기간은 최대 366일이다. 보고서는 읽기 전용 트랜잭션에서 집계 JSON 한 건만 반환한다. 계정 ID, 익명 세션 해시, 로그인 시도 nonce는 출력하지 않는다.

## 지표 해석

`anonymousGuideEngagement`는 조회 구간 안에서 익명 세션·가이드별 첫 `signup_guide_view`를 코호트 기준으로 삼는다. 이후 같은 익명 세션과 같은 가이드에서 발생한 CTA만 인정한다. 모든 가이드 조회를 분모로 `anyCta`, `verifyCta`를 계산하며, 첫 조회의 채널·랜딩·가이드·브라우저·OS·언어·audience를 차원으로 사용한다. `unknown` audience는 전체 참여율에 포함하고 별도 건수로 표시하지만 guest 가입 전환 분모에는 넣지 않는다.

`guestVerifyToLogin`은 각 익명 세션·가이드의 첫 인증 CTA를 기준으로, 그 시점의 audience가 `guest`인 세션을 대상으로 한다. 첫 CTA가 `unknown`이면 이후 CTA를 기준으로 다시 분류하지 않는다. 첫 조회가 `unknown`이어도 CTA 시점에 `guest`이면 포함하고, 첫 조회가 `guest`여도 CTA 시점에 `member`이면 제외한다. 조회 이벤트가 없더라도 유효한 guest 인증 CTA는 이 코호트에 포함한다. `unknown` 인증 CTA는 `unknownAudienceVerifyCtaSessions`로 따로 표시한다. 인증 CTA 뒤 처음 발생한 `trigger=provider` 로그인 시도를 선택하고, 같은 nonce·익명 세션·가이드·provider·trigger의 성공만 인정한다. 첫 시도가 실패하고 두 번째 시도가 성공한 경우 첫 시도의 성공으로 합치지 않는다.

`loginAttempts`는 조회 구간 안에서 시작한 시도를 집계한다. 결과는 같은 nonce·익명 세션·가이드와 일치하는 provider·trigger만 연결한다.

- `succeeded`: 성공 관찰이 있는 시도
- `failedWithoutSuccess`: 실패는 있으나 성공은 없는 시도
- `pending`: 실패와 성공이 모두 없는 시도
- `recovered`: 같은 시도에서 실패와 성공이 모두 관찰된 경우

`byTrigger`는 `provider`, `session_restore`, `retry`, `reauth`를 분리한다. 실패 내역은 브라우저·provider·stage·reason 조합별 건수만 반환한다. 연결할 시작 이벤트가 없거나 provider·trigger 등이 맞지 않는 결과는 `unmatchedOrInconsistentResultObservations`로 표시한다.

`canonicalSignupProgress`는 조회 구간에 생성된 `app_users`를 기준으로 같은 계정의 프로필과 팬 패스포트가 종료 시각 전에 생성됐는지 계산한다. 테스트 계정은 자동으로 제외하지 않는다. 활성 관리자 허용 목록과 이메일이 일치하는 계정 수는 `adminAllowlistedAccounts`로 따로 제공한다.

`projectionCoverage`는 원본 `app_users`, `user_profiles` 수와 정확히 대응하는 서버 이벤트 수를 비교한다. 이 값은 누락된 측정 이벤트를 찾기 위한 지표이며 가입 완료의 원본 수치를 대체하지 않는다. 모든 전환율은 분모가 0이면 `null`이다.

## 로컬 검증

다음 명령은 임시 PostgreSQL 클러스터에 전체 마이그레이션을 적용한 뒤 기존 백엔드 보안 검사와 가입 측정·보고서 fixture를 실행한다.

```bash
bash scripts/verify-backend-security.sh
```

fixture는 고정 속성 검증, 멱등 재실행과 충돌, 서버 원본 검증, private ACL, INSERT 전용 프로젝션, 측정 실패 시 원본 보존, 트랜잭션 롤백, 빈 분모, 순서가 맞는 전환, 누락·재시도·대기·복구 상태, 서로 다른 로그인 시도 혼동 방지를 검사한다. 임시 데이터베이스는 검증 후 전체 삭제한다.

## 2026-09-12 로그인 복구와 계측 충돌 개선

초기 점검 구간은 9월 11일 23:31~12일 01:16 KST다. 로그인 41회 중 성공 22회, 시간 초과 8회, 결과 미관측 11회가 기록됐다. 시간 초과는 지갑 준비 6회와 세션 처리 2회다. 실패 8회 중 6회는 같은 익명 세션·가이드에서 이후 다른 시도의 성공이 확인됐지만, 이를 6명의 복구로 해석하지 않는다.

지갑 생성 SDK 대기가 30초를 넘으면 같은 계정의 최신 상태를 한 번 더 조회한다. 조회는 최대 5초로 제한하며, 해당 계정의 Privy 내장 Ethereum 지갑이 확인된 경우에만 기존 토큰·서버 검증으로 진행한다. 지갑 없음, 외부 지갑, 다른 계정, 조회 실패·시간 초과에는 세션을 생성하지 않는다. 계정 전환·화면 종료 뒤의 결과는 무시하고, 원래 지갑 생성 작업이 끝나기 전에는 추가 생성하지 않는다. 이 복구 경로는 로컬에서 재현한 조건에 대한 개선이며, 운영에서 관측한 지갑 시간 초과 6건의 원인이 확정됐다는 뜻은 아니다.

기존 페이지 조회 이벤트는 같은 중복 방지 키로 새 전송 시각을 만들 수 있었다. 서버가 시각과 전체 내용을 엄격히 대조하므로 반복 전송이 충돌하는 조건을 재현했다. 같은 페이지 조회의 재전송은 최초 전체 내용을 유지하고, 익명 세션과 기존 인증 계정의 범위를 구분한다. 브라우저 캐시는 수량·기간을 제한하고 토큰은 저장하지 않는다. 서버의 충돌 판정은 유지한다. `signup_guide_*`, `login_*`, 계정·프로필 원본 프로젝션의 측정 정의는 바꾸지 않는다.

운영 진단 로그는 다음 점검에 사용한다.

- `product_event_idempotency_conflict`: 검증된 이벤트명, 고정 충돌 사유, HTTP 409만 기록한다. 초기 409 응답 98건은 이벤트 종류가 확인되지 않았으므로 모두 페이지 조회 또는 가입 계측 문제로 소급 분류하지 않는다.
- `[auth/session] timing`: 인증 제공자 조회와 DB 저장소 동기화의 소요 시간, 요청 결과, 실패 당시 단계를 기록한다. 내부 단계 시간 초과와 전체 요청 시간 초과를 구분한다. 종료 결과는 한 번만 기록하며 늦은 완료를 성공으로 덮어쓰지 않는다.
- 두 로그에 계정·익명 세션 ID, 지갑 주소, 이메일, 토큰, 중복 방지 키, 요청 본문, 외부 오류 원문을 기록하지 않는다.

로컬 로그인 테스트 55개가 통과했다. 실제 LoginPage와 CSS를 렌더링하는 Chromium 390×844·1440×1000 fixture에서 지갑 재확인 후 세션 요청 1회, 지갑 미확인 시 오류 안내와 재시도 버튼, 가로 넘침 없음, page error 없음을 확인했다. Privy·세션 API는 합성 응답이며 운영 OAuth 검증을 뜻하지 않는다. 관련 근거는 `artifacts/signup-conversion-routine/browser-check/`에 보존한다.

다음 정기 점검은 배포된 정확한 커밋을 확인한 뒤 지갑 단계 시간 초과·후속 재시도 성공, 세션 단계별 시간, 이벤트명별 충돌을 비교한다. 배포 시작만으로 두 문제를 해결 상태로 바꾸지 않는다. 실제 유입이 있는 관찰 구간에서 확인하며, 전환율 개선 효과는 별도로 판단한다. 이번 변경에는 DB 마이그레이션이나 인증 제공자 설정 변경이 없다.

DB·컨트랙트 검증은 [기존 Backend security 성공 실행](https://github.com/ByUs-FanPassport/ByUs/actions/runs/34616440477)의 근거를 재사용한다. 해당 커밋 `10f7ae9`부터 이번 작업의 기준 main까지 `supabase/`, DB 보안·마이그레이션 재생성 스크립트, `contracts/`에 차이가 없고 이번 변경도 해당 파일을 수정하지 않았다. 변경된 로그인·진단·계측 코드의 검증은 별도로 수행한다.

최종 검증에서 계측 클라이언트·서버·호출부를 포함한 6개 파일 132개 테스트가 통과했다. 이후 계정 전환·화면 종료 시 늦은 계측 전송을 차단하는 수정은 해당 호출부 3개 파일 120개 테스트로 확인했고, 나머지 변경 없는 테스트의 성공 근거는 재사용했다. 세션 진단·실제 POST 핸들러·로그 비노출 검증은 3개 파일 12개 테스트가 통과했다. 최종 통합 타입 검사와 변경 TypeScript 파일 린트도 통과했다. 독립 검토에서 지갑 복구, 진단 로그, 계측의 계정 전환 경계를 승인했다. 테스트 개수는 서로 겹치는 실행 단위이므로 합산하지 않는다.

## 2026-09-12 지갑 대기 진단

지갑 준비 시간 초과의 원인을 구분하기 위해 `login_result`에 아래 선택 속성 4개를 함께 추가한다. 기존 11개 속성 형식도 계속 허용한다. 별도 이벤트·식별자·계정 연결은 만들지 않는다.

| 속성 | 허용 값 |
|---|---|
| `walletWaitOutcome` | `succeeded`, `timeout`, `error` |
| `walletWaitMs` | 현재 동기화 시도에서 SDK 결과를 기다린 시간, 정수 0~120000ms |
| `walletReconciliation` | `not_needed`, `wallet_found`, `wallet_missing`, `timeout`, `error` |
| `walletReconciliationMs` | 재확인 대기 시간, 정수 0~30000ms |

시간은 단조 시계를 사용하고 상한을 넘으면 상한값으로 기록한다. 이는 시간 초과 설정이 아니다. 기존 30초 SDK 대기·최대5초 재확인 제한을 유지한다. 이전 시도의 SDK 작업을 재사용하면 새 시도가 기다린 시간만 기록하며, 최초 지갑 생성 작업 전체의 소요 시간이라고 해석하지 않는다. 시계를 읽지 못하면 선택 진단을 생략한다.

SDK 성공·오류에는 재확인 `not_needed`와 시간0을 붙인다. SDK 시간 초과에는 재확인 결과를 기록하며 `not_needed`는 허용하지 않는다. 재확인 후 지갑이 없었던 경우와 조회 자체가 실패하거나 시간 초과된 경우를 구분한다. 지갑이 준비되지 않은 진단은 지갑 단계 실패에만 붙일 수 있다. 기존 지갑이 있어 생성 대기를 하지 않았던 로그인에는 필드를 붙이지 않는다.

진단은 해당 동기화 실행 안에서만 보존하고 기존 익명 로그인 결과로 전송한다. 브라우저 저장소에 추가로 남기지 않는다. 같은 결과 중복 방지·계정 전환·화면 종료 경계를 유지하며, 늦게 끝난 SDK 작업이 이미 기록한 진단을 바꾸거나 추가 결과를 보내지 않는다. 클라이언트에서 진단이 잘못되면 진단만 생략하고 기본 결과는 전송한다. 서버와 DB는 부분 필드·잘못된 타입·범위·조합을 거부한다.

보고서의 `walletDiagnostics`는 **관측된 login_result에 포함된 지갑 대기**를 집계한다. 고유 사용자나 모든 SDK 실행 수가 아니다. 기존 중복 방지 정책에 따라 같은 시도·같은 outcome의 후속 관찰은 추가되지 않는다. `withoutDiagnosticResultObservations`에는 구버전 앱, 지갑 대기가 필요 없던 로그인, 시계·진단 정보가 유효하지 않았던 결과가 함께 들어갈 수 있다. 진단 없는 결과를 모두 구버전 또는 오류0으로 간주하지 않는다.

배포 순서는 호환 DB 검증 함수 변경 후 애플리케이션이다. 새 필드는 선택 항목이므로 앱을 이전 정상 커밋으로 되돌려도 기존 이벤트를 계속 받는다. 되돌릴 때 저장된 데이터를 삭제하거나 전체 DB를 롤백하지 않는다. 확인 목표는 실제 시간 초과 결과의 SDK 대기와 재확인 결과를 구분하는 것이며, 진단 배포 자체를 운영 지갑 문제 해결이나 전환 개선으로 보고하지 않는다.

지갑 진단의 로컬 검증은 로그인 64개 테스트(30초/5초 측정, 공유 SDK 재시도의 현재 대기2초, 늦은 완료·계정 전환·화면 종료 포함), 계측 도메인·tracker·클라이언트·실제 API 핸들러 28개 테스트, 타입 검사와 변경 파일 린트가 통과했다. 전체 백엔드 검증에서 150개 마이그레이션 재생성과 기존 보안·동시성 검사가 통과했다. 진단이 있는 결과 6건과 없는 결과 2건의 집계, 시작 없는 결과 제외, 재확인별 그룹·시간 상한도 fixture로 확인했다. 테스트 개수는 실행 단위이며 이전 실행과 합산하지 않는다. 독립 보안 검토에서 TS·SQL의 의미 검증과 기존 권한 유지를 승인했다.

운영 DB에는 `20260912075217_wallet_login_diagnostics.sql`을 기존 함수 본문 일치 확인 후 단일 트랜잭션으로 적용했다. 함수 본문 MD5는 `8e58357bb8ce50dd99bfacdb142865d4`에서 `660b1c2acb215102b4b48e6699b55b40`으로 변경됐으며, 실행 권한은 기존 postgres·service_role만 유지했다. 마이그레이션 이력과 본문 일치를 확인했다. 운영에 합성 가입·진단 이벤트를 생성하지 않았다. 앱 반영 이후 실제 진단 수집과 시간 초과 원인은 후속 루틴에서 확인한다.
