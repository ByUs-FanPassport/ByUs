# ByUs 텔레그램 운영 알림 확장

기준: 2026-09-21. 사용자 선택은 **모든 주요 활동의 실시간 알림**이다. 일일 요약을 주 전달 방식으로 삼지 않는다.

## 프로젝트 맥락

ByUs는 크리에이터 발견 → 가입·팬 인증 → 팬 패스포트·응원·LIVE 참여 → 응모권·경품 응모 → 당첨·수령으로 이어지는 팬 참여 서비스다. Supabase의 업무 원장이 실제 활동의 기준이며, 별도의 익명 계측은 행동 관찰 자료다. 자격·보상·민팅 처리를 알림 기능이 바꾸면 안 된다.

이미 BYUS-ALERT에 가입·팬 가입·예약·출석·추첨 결과·CS 접수/답변·캠페인 첫 방문이 전달된다. 인증 사진 검토와 /users, /today, /lives, /help도 구현되어 있다. 현재 구조는 DB outbox, 방 제한, claim/begin/finish, 중복 방지, 최대 5건 묶음, 1분 워커다. 7일 알림 원장 203건(검증용 기록 포함), 대기 0건을 관측했다. 이 수치는 사업 활동 전체 수치가 아니다.

가입 안내·로그인 관찰은 익명 세션이며 실제 계정 생성과 임의로 연결하지 않는다. 캠페인 방문→외부 이동률은 응모 전환율이 아니다. 조회 범위·분모·측정 한계를 메시지에도 유지한다.

## 공식 사례 비교와 적용

| 출처 | 확인한 방식 | ByUs 적용 판단 |
|---|---|---|
| [PostHog Alerts](https://posthog.com/docs/alerts) | 고정·상대·이상치 조건으로 지표 변화를 감시하고 Slack/Webhook으로 전달 | 활동 알림과 지표 해석을 구분한다. 아직 보정하지 않은 급등·급락 임계값은 자동 경보로 만들지 않는다. |
| [Mixpanel Alerts](https://docs.mixpanel.com/docs/features/alerts) | 이벤트·세그먼트 조건, 알림 빈도 제한, 과거 구간 테스트와 테스트 발송 | 비교 보고에는 기간·현재값·이전값·분모를 함께 제공한다. 운영 반영 전 fixture와 실제 발송 응답을 검증한다. |
| [Sentry 알림](https://www.sentry.help/en/articles/15007504-monitors-alerts-guide-and-faq) | 문제 탐지와 알림 전달을 구분하고 새 문제·재발·해결 상태를 다룸 | 발급 완료·최종 실패, 전송 최종 실패·결과 불명처럼 확인이 필요한 상태 변화를 알린다. 재시도 중간 상태를 매번 새 실패로 보내지 않는다. |
| [Grafana 알림 묶기](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/group-alert-notifications/) | 관련 알림을 묶고 첫 대기·후속 묶음·반복 주기를 구분 | 원장 사건은 각각 보존하고 메시지 표현만 묶는다. 5건 초과는 다음 발송으로 넘긴다. 오래된 활동부터 순서대로 처리하고, 실패는 경고 표시로 구별한다. |
| [Telegram Bot FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this), [retry_after](https://core.telegram.org/bots/api#responseparameters) | 그룹당 분당 20개 제한, 429 응답의 대기 시간 제공 | 기존 제한과 retry_after를 유지한다. 응답이 불명확한 전송은 자동 재발송하지 않고 delivery_unknown으로 보존한다. |

위 자료는 제품 동작의 근거다. 공급사의 성과 주장이나 예시 임계값을 ByUs에서 검증된 효과로 취급하지 않는다. 'critical 10초' 같은 새 SLA도 현재 1분 워커에 약속하지 않는다. 평상시 다음 실행 주기에 발송하며, 밀린 경우 순차 전달한다.

## 적용 원칙

- 서버에서 확정된 주요 활동과 상태 변화만 기록한다. 중복 요청·동일 상태 UPDATE·실패한 트랜잭션은 새 알림이 아니다.
- 신규 알림은 공개 콘텐츠명·건수·처리 상태·관리자 링크만 담는다. 새 개인정보나 인증 사진·주소·오류 원문을 추가하지 않는다.
- 메시지는 '무슨 활동/변화인가 → 관련 대상·수량 → 확인할 관리자 화면'으로 구성한다.
- 운영 실패는 실제 상태를 근거로 표시하며, 임의의 AI 원인 진단을 보내지 않는다.
- 마케팅 판단은 실제 수치와 확인할 가설을 분리한다. 광고 집행·예산 변경·고객 메시지 발송을 자동 실행하지 않는다.
- 기존 그룹과 워커를 재사용한다. 새 유료 서비스나 별도 알림 플랫폼을 추가하지 않는다.

## 이번 적용 범위

기존 8개 알림에 20개 활동 유형을 추가했다. 응모(사용 응모권 포함), 기존 혜택 수령, 리액션, 미션 제출, LIVE 여정 완료, 컬렉터블 수령, 초대 참여, 인증 승인·반려, 경품 배송·수령 상태 및 미수령 마감, 사업 문의 접수·메일 전송 문제, 온체인 발급 완료·최종 실패, 팬 알림 전송 문제, LIVE 공개·취소·일정 변경, 뱅크시 외부 링크 이동 요청이다. 정기 LIVE의 공개 INSERT도 포함하며 생성 직후 제목 번역이 아직 없으면 slug를 표시한다.

인증 검토 요청은 기존 사진 검토 워커를 유지한다. 개인정보가 포함된 기존 가입/CS 메시지는 기존 범위이며 신규 유형에는 이름·이메일·초대 코드·주소·증빙·오류 원문을 넣지 않는다. 사업 문의는 담당 메일함 확인 안내만 보낸다. 관리자 링크는 실제 `/admin/benefits`, `/admin/celebrities` 등으로 연결한다.

`/ops`는 CS·인증 대기, 발급 실패·지연, 팬 알림 전송 문제, 사업 문의 메일, Telegram 큐를 조회한다. 30분 지연은 기존 운영 SQL 보고서의 기준을 재사용한 조회 항목이며 자동 장애 임계값이 아니다. 이메일 결과 불명은 메시지에서 구분하고, 정상 취소·자격 변경·대체 채널 전송 대기는 장애로 알리지 않는다. 워커 자체가 중단되면 Telegram도 전송할 수 있으므로 이 명령은 독립적인 가동 감시가 아니다.

`/marketing`은 최근 7개 KST 날짜(오늘 진행분 포함)와 이전 동일 길이를 비교한다. 신규 계정 중 기간 종료 전 프로필·팬 패스 발급을 마친 계정, 리액션·미션·응모·사용 응모권·초대 참여를 집계한다. 뱅크시 링크별 첫 출처 방문과 같은 방문 세션의 외부 이동 요청을 상위 5개까지 표시한다. 운영·테스트 계정도 포함한다. `/today`는 기존 오늘 현황 조회를 유지한다.

마케팅 실행 순서는 출처별 링크 게시 확인 → 신규 계정의 팬 패스 진입 점검 → 동일 콘텐츠의 출처별 방문/외부 이동 비교다. 출력된 확인 후보는 원인 확정이나 광고 성과 보장이 아니다. 유입별 응모 전환·매출·광고 수익률은 현재 데이터로 산출하지 않는다.

## 전달 및 측정 한계

기존 1분 실행·회당 5건 한도를 유지한다. 밀린 알림은 순차 처리하며, 기존 정책상 24시간 넘게 대기한 기록은 건너뛴다. 따라서 무제한 유입의 모든 메시지 전달이나 초 단위 지연을 보장하지 않는다. Telegram 발송 이력은 기존 30일, 익명 캠페인 기록은 승인된 90일 보관이다. 결과 불명은 중복 방지를 위해 자동 재발송하지 않는다.

전송·발급의 모든 중간 재시도, 원시 페이지뷰, 공개 전 당첨자, 보상 원장의 중복 회계 기록은 별도 주요 활동으로 보내지 않는다. 카카오의 공급사 접수 후 배달 결과를 기다리는 상태는 기존 전송 워커가 판정하며, plan의 최종 실패 때 전달한다. 별도 일일 예약 보고·유료 AI·자동 광고 집행은 이번 적용에 포함하지 않았다.
